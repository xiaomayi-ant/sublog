# 首页河流 —— 数学方案、调优记录与利弊评估

> 代码：`src/lib/riverMath.mjs`（纯函数几何）、`src/lib/riverRenderer.mjs`（Canvas 2D 渲染）
> 消费方：`src/components/HomeRiver.astro`（首屏）、`src/pages/lab/river.astro`（参数实验室）
> 测试：`tests/river-math.test.mjs`、`tests/river-palette.test.mjs`、`tests/river-lab-contract.test.mjs`、`scripts/verify-river-lab-mutations.mjs`
> 视觉基线：`npm run visual:check`

---

## 1. 方案总览

这条河不是一张图，也不是一段视频，而是**每帧按参数方程算出来再画的**。整体分三层，从下到上：

| 层 | 函数 | 画什么 | 视觉职责 |
|---|---|---|---|
| 水彩 | `drawWash` | 8 条同心缎带，由宽到窄 | 河的体积与深浅 |
| 纤维 | `drawFibers` | 50 条沿河道的虚线 | 河床纹理 + **流动感** |
| 焦散 | `drawLight` | 3 股细亮纹 | 清澈感 |

三层共用同一条**中心线**。理解这条河只需要抓住一句话：

> **河道是确定的，水在河道里流。**

岸线几乎不动（横穿全河约 230 秒的漂移，近乎静止），流动完全由描在河道上的条纹平移产生。这是刻意的选择——如果让岸线上下摆动，读出来是一条**丝带**，不是一条河。

## 2. 几何：从一条线到一条河

### 2.1 中心线 `sampleCenterline(s, options)`

`s ∈ [0,1]` 是沿河的归一化位置，返回归一化坐标系里的一个点。它由四项叠加：

```
y(s) = 0.51
     + bend × [ 长波 + 滚动形变 ]
     + 有机抖动
```

- **长波** —— 两个不同频率的正弦叠加（`sin(π·1.82s)` 与 `sin(π·4.1s)`，振幅 0.115 / 0.055）。两个不可通约的频率保证河不会读成规则波浪。
- **滚动形变** —— 两个高斯包络（中心 0.52 与 0.79）随 `progress` 变化。首页 `progress` 恒为 0，只有 lab 页用到滚动驱动。
- **有机抖动** —— 一维噪声，振幅仅 0.045 × turbulence，时间系数 0.02（极慢）。

### 2.2 河宽 `riverWidth(s, options)`

```
width(s) = 0.091 × 宽度控制 × 不规则度 × 下游盆地 × 源头收缩
```

- **不规则度** `0.88 + 0.17·noise` —— 河宽本身也不是常数
- **下游盆地** `1 + 0.34·gaussian(s, 0.72, 0.2)` —— 下游有一处开阔
- **源头收缩** `0.78 + 0.22·min(1, s/0.17)` —— 上游窄一些

### 2.3 两岸 `buildRibbonGeometry` + `ribbonEdges`

沿中心线的切线求法线，两侧各推半个河宽。**两个非平凡的处理**，也是这套方案里最有价值的部分：

#### 各向异性校正（aspect correction）

中心线活在归一化单位方格里，但画到的是非方形画布。若直接在单位方格里求法线，画出来的河宽会**随方向变化**——横着的河段厚、斜着的薄。

做法是把 x 乘以 `aspect` 统一到"画布高度"单位里求切线与法线，得到的偏移再除回 `aspect`：

```js
const deltaX = (after.x - before.x) * aspect;   // 进入等距空间
const offsetX = (normal.x * halfWidth) / aspect; // 出来回归一化空间
```

变异测试 `unaspected-ribbon-tangent` 和 `anisotropic-bank-offset` 各守一半。

#### 曲率钳制（cusp limit）

弯道内侧，若半宽超过曲率半径，两岸会自交折出**尖点**。判据是 `半宽 × 曲率 < 1`，这里取 0.78 留 22% 余量。

关键在于**用软饱和而不是 `Math.min`**：

```js
halfWidth × (1 + ratio^4)^(-1/4)
```

硬截断会在钳制生效处留下宽度突变的折痕；软饱和让平缓河段几乎不受影响，只在临界处收窄。变异测试 `disabled-curvature-limit` 守着它。

### 2.4 缎带的填充：扫掠并集（swept union）

相邻两个采样点之间填一个四边形，**同时在每个采样点画一个半径等于半宽的圆**。圆补上四边形在转角处留下的缺口，这是 `data-river-join="swept-union"` 的含义。变异 `naive-ribbon-join` 守着它。

## 3. 噪声：从单倍频到 fbm 与域扭曲

### 3.1 基础噪声 `smoothNoise`

一维值噪声：整数格点上取哈希，用五次平滑函数 `6t⁵-15t⁴+10t³` 插值。确定性、有界 `[0,1]`、局部连续。

### 3.2 fbm（分形布朗运动）

把同一种噪声按倍频叠起来，振幅每层减半：

```
fbm(x) = Σ (0.5^i · noise(x · f_i))  /  Σ 0.5^i        f_i = 2.03^i
```

两个细节：

- **频率步进取 2.03 而非 2** —— 整数倍频会让各层的峰周期性对齐，叠出肉眼可见的规律条纹
- **结果归一化回 `[0,1]`** —— 与 `smoothNoise` 同值域，调用处 `(x-0.5)×幅度` 的写法不必跟着改

### 3.3 域扭曲（domain warp）

先用一层噪声去偏移采样坐标，再在偏移后的坐标上取噪声：

```
warpedFbm(x) = fbm( x + (fbm(x·0.5) - 0.5) · strength )
```

直接叠噪声得到的是"原地起伏"；扭曲之后纹理是**被流动拖着走**的。

### 3.4 接入点与红线

| 位置 | 改前 | 改后 |
|---|---|---|
| `drawWash` 的 pulse（河岸轮廓） | 单倍频 | fbm |
| `drawFibers` 的 flutter（河道内部纹理） | 单倍频 | fbm |
| `drawLight` 的 wander（焦散亮纹） | 两个正弦 | 域扭曲 fbm |

**刻意没碰的两处**：

1. **中心线本身** —— 碰它就破坏"河道静止"的模型，河会变成丝带。
2. **纤维的 `laneRadius` 与 `shear`** —— 这两个噪声按 `fiber` 缓变而非按 `s`，正是"相邻纤维平滑过渡所以读作剪切、不是各走各的"的来源。换成 fbm 会把那个梯度打碎。

## 4. 流动：虚线偏移

这是整套方案里最巧的一手，也是"河道静止、水在流"的实现：

```js
context.setLineDash([dashUnit, dashUnit*0.85, dashUnit*0.22, dashUnit*0.7]);
context.lineDashOffset = -(time * flow + fiber * dashUnit * 0.045);
```

纤维路径**完全静止**，动的是描在它上面的虚线相位。速度取自明渠流的横向速度剖面：

```js
laneFlow(lane) = max(0, 1 - lane²)     // 抛物线：贴岸不动，河心最快
```

再叠一点逐条的剪切差异，免得整条河像刚体在平移。

**相位相干性是关键**：各纤维之间只小幅错开（0.045 个周期）。曾用 0.37 时，任意一列上总有一部分是亮段、总量恒定，读起来是**闪烁**而不是平移。

## 5. 调优记录

四次改动，每次都有可复现的量化验收。基线工具见 `npm run visual:baseline` / `visual:check`。

### 5.1 视觉基线（前置）

改渲染器之前先建立一个能回答"像素动了没有"的东西。

- 确定性来自 `--force-prefers-reduced-motion`：渲染器在该分支把 `time` 固定为 0，同一份产物每次画出同一帧。实测三次 sha256 一致，因此比对用哈希即可，不必引图像 diff 库。
- **负向验证过**：把最深一档水色单通道改 28/255，三张截图全部报差异、退出码 1。只会说"没变"的比对工具没有意义。
- 覆盖 1440×900 与 390×844（卡在 `bendScale` 的 `min(1, aspect/1.6)` 分界两侧）以及 lab 页。
- **刻意不挂进 `npm test`**：那条链是生产部署的闸门，不该因为一个浏览器二进制不在预期位置而挡住发布。

**局限**：只覆盖静态形态。流动本身截不到——无限 RAF 循环让 `--virtual-time-budget` 耗不尽，截图会挂死（实测超时过一次）。那部分由变异测试 `disabled-animation-loop` 守。哈希跨 Chrome 版本会变，manifest 里记了采集时的版本。

### 5.2 性能：按帧缓存河道几何 ✅ 效果显著

**问题（实测，非估算）**：河流单帧 **28.5ms**，而 60fps 的整帧预算是 16.7ms —— 超了 1.7 倍，整页只有 48fps。

测法：RAF 回调按注册顺序执行，河的循环先注册，所以在后注册的回调里 `performance.now() - timestamp` 就包含它这一帧的开销；再用 IntersectionObserver 做天然对照组（滚出视口 → `visible=false` → `render()` 直接返回，测得 0.5ms）。dev 与 production 构建数字一致，排除开发服务器假象。

**根因**：同一份几何被反复求值。八层水彩、五十条纤维、三股亮纹各有自己的 `s` 网格，但**同一个 `s` 上的中心线、法线、曲率、河宽对所有图层是同一份**，却每层从头算一遍。纤维和亮纹更亏——它们调 `buildRibbonSample(s, 0, …)` 只为拿 `center`，付了六次中心线采样加一次曲率，再把两岸整个扔掉。

**做法**：把 `buildRibbonSample` 拆成两半——`buildRibbonGeometry`（与半径无关，可缓存）和 `ribbonEdges`（与半径有关，每层各算）。渲染器按采样数缓存前者，**每帧清一次**（`options` 随 `time` 变，跨帧复用会把河冻住）。

同一帧的几何求值从约 **7900 次降到 403 次**。

| 指标 | 改前 | 改后 |
|---|---|---|
| 河流单帧（中位） | 28.5ms | **4.0ms** |
| 河流单帧（p95） | 39.4ms | 5.9ms |
| 整页 | 48.2fps | **60.2fps** |

验收：三张基线**逐像素不变**；压在 `riverMath` 上的三条变异重构后依然被杀（证明拆分没把它们摘出执行路径）；浏览器里对画布连取三次样确认河仍在动（排掉"缓存忘清导致冻结"）。

**原计划里的自适应质量档没有做**：测完发现不需要。4.0ms 落在 16.7ms 预算内，再加降级只是徒增复杂度，还会牺牲 dpr 换来的锐度。

### 5.3 质感：fbm + 域扭曲 ⚠️ 效果远低于预期

**结果如实记录**：与改动前相比 7.3% 的像素有变化，平均色差 **2.76/255**，最大 19，色差大于 4 的只占 1.34%。

**这是特征的改变，不是可见度的改变。** 原因是这条河的幅度本来就调得极克制：wash pulse 只有 ±5% × turbulence(0.48) ≈ ±2.4%，fiber flutter 幅度 0.006。河是一层淡背景，任何在原幅度内的纹理改动都很难被看见。

性能代价被上一步吸收：每帧多出约 7300 次噪声求值，单帧 4.0 → 4.5ms，整页仍 60fps。

**评估**：改动本身是对的（多尺度纹理、非周期焦散），但**"fbm 是像水与像丝带的分界"这个说法在当前幅度下过头了**。要让它可见必须动幅度，那是艺术方向的决定。

### 5.4 色板：尝试对齐 tokens.css → 已回滚

`riverRenderer` 里曾有一句注释声称"前三档对应 `tokens.css` 的 `--water-100/300/500`，最深一档是 `--color-river #1651be`"。**那是错的**：

| | tokens.css | 渲染器实际 | 差 |
|---|---|---|---|
| water-100 | `#c8f1ee` | `#defcfa` | (22,11,12) |
| water-300 | `#84dcd9` | `#8cf0ec` | (8,20,19) |
| water-500 | `#4ab8ca` | `#4ed4e4` | (4,28,26) |
| 最深档 | `#1651be` | `#4298e4` | **(44,71,38)** |

按注释把两边对齐之后：28.6% 像素变化、平均色差 12.32、绿通道平均降 12.1 —— 河从青绿转向蓝。**观感偏离过多，已回滚**，颜色逐位恢复（哈希与回滚前完全一致）。

**保留下来的结论**：两条色阶本来就该是两套值，用途不同——`--water-*` 要承载文字、背着论证过的对比度；`WASH_LADDER` 只做图形、在 alpha 0.03~0.09 下叠出来。真正成立的命题不是"逐值相等"，而是"**同一条色相轴**"（实测色相差 0.4°/0.4°/2.0°/9.6°/10.8°）。契约测试因此守色相同族，阈值 14°。

顺带清掉了核心渐变里散写的四个色标（含一档 `rgb(96,182,250)` 不属于任何色阶，谁也没提过）。

## 6. 利弊评估

### 优势

1. **几何层是纯函数，可单元测试。** `riverMath.mjs` 不碰 DOM、不存状态，15 条测试 + 3 条变异直接压在它身上。这是这套方案最大的结构优势——绝大多数"背景动效"是没法这样测的。
2. **曲率钳制与各向异性校正是真功夫。** 这两处解决的是参数曲线加宽的固有缺陷（尖点、厚薄不均），不是调参能绕过的。软饱和取代硬截断这一手尤其漂亮。
3. **"河道静止 + 虚线相位平移"** 用极低成本换到了可信的流动感，且相位相干性被显式论证过。
4. **零依赖、零网络。** Canvas 2D，无着色器、无库，`file://` 都能跑。
5. **降级路径完整。** `prefers-reduced-motion` 下渲染静态帧，IntersectionObserver 离屏停渲，dpr 上限 1.75。

### 劣势与已知代价

1. **CPU 成本仍然显著。** 优化后 4.0ms/帧是桌面 Mac 的数字。移动端**没有任何降级**——`@media (max-width: 44rem)` 只是把 canvas 调到 `opacity: 0.72`，该算的一次没少。低端手机上的实际表现**没有测过**，这是当前最大的未知。
2. **`ribbonBuffer` 是 CSS 像素分辨率**，而主 context 做了 `setTransform(pixelRatio,…)`，所以水彩层实际被放大 1.75× 画上去。河岸边缘天然是软的——水彩感可能正来自于此，但这是**未经声明的副作用**，不是设计决定。
3. **视觉基线只覆盖静态帧。** 流动的正确性目前只有"动画循环没被删掉"这一条保障，没有任何东西验证流速、相位相干性或方向。
4. **参数之间高度耦合。** `bend / width / turbulence / layers / flow / cobalt` 六个控制项互相影响（例如 bend 变大会触发曲率钳制、间接改变观感宽度）。lab 页能调，但没有任何一处记录"哪些组合是坏的"。
5. **幅度调得太克制，改进空间被压死。** 5.3 的教训：在现有幅度内做纹理改动几乎不可见。想要观感上的实质变化，必须先决定是否放开幅度——这是设计问题不是技术问题。
6. **既有的无障碍缺陷**（见下节）。

## 7. 首屏问句的对比度（已修）

测性能时顺带量到的，**不是这轮改动引入的**：

| 首屏问句 | 修复前 | 修复后 | WCAG AA 小字 |
|---|---|---|---|
| 中文（15.7px） | 4.12:1 | **5.94:1** | 4.5:1 |
| 英文（14.1px） | 2.35:1 | **5.29:1** | 4.5:1 |

### 根因

不在河，在**文字自带透明度**。带 alpha 的墨会与身后的底混合，所以对比度取决于身后是什么：

| | 白底 | 河面（最暗 `rgb(177,212,231)`） |
|---|---|---|
| `--color-ink-soft` (0.72) | 4.84:1 ✅ | 3.81:1 ❌ |
| `--color-ink-faint` (0.46) | **2.48:1 ❌** | 2.22:1 ❌ |

河再淡，混进来的也是比白更暗的一层，所以同一个 alpha 到了这里就掉一档。

`HomeRiver.astro` 里记录作者当年为标题区实测过 10.17:1，并据此删掉了原来那个白椭圆（"白椭圆换来的 1 点对比度，代价是把河的左半边洗掉了"）。那次只测了标题——大字 AAA 只需 4.5:1，现测 6.98:1 仍宽裕——**没测这两行小字**。

### 修法与取舍

**没有加底板**：作者已经明确否决过那条路，重新加回去是无视既有决定。**没有改全局 token**：`--color-ink-soft` 在白底上是达标的，问题只出在河这个上下文。

改为在 `tokens.css` 里派生两档专供压在河上的文字（遵守该文件"不再各处自造 rgba"的约定）：

```css
--color-ink-on-water:       rgba(76, 54, 48, 0.88);  /* 5.47:1 */
--color-ink-on-water-faint: rgba(76, 54, 48, 0.82);  /* 4.77:1 */
```

层次的代价要说清楚：中英两行原来的 alpha 差是 0.72 / 0.46，现在是 0.88 / 0.82，**色彩上的层次明显变弱了**。理由是源码里对英文行的设计意图写得很清楚——"换回编辑体斜体，它和标题同源，读作同一句话的另一种写法"——层次本来就主要由**斜体衬线字体和更小的字号**承担，颜色只是次要强化。把字淡到读不清不是层次，是缺陷。

契约测试 `tests/river-palette.test.mjs` 钉住两条：两档在最暗河面上都 ≥4.5:1；英文行仍必须比中文行淡（修对比度不能把层次一起修掉）。负向验证过——把 alpha 调回 0.46，测试立刻变红。

那个最暗河面常量是量出来的：1345×669、dpr 2 下对问句区域连采 40 帧取最暗像素。**河的色阶若调深，必须重新量并更新它。**

### 仍未解决

`--color-ink-faint`（0.46）**在白底上就只有 2.48:1**，全站约 40 处在用（正文元信息、日期、次级说明）。这是独立于河的全站问题，改动波及面大，本次未动。

## 8. 如何验证

```bash
npm run visual:baseline     # 采集视觉基线（改渲染器之前）
npm run visual:check        # 与基线比对（改完之后）
npm run test:river:math    # 几何与噪声的纯数学测试
npm run test:river:palette # 色阶契约
npm test                   # 完整门禁，含变异测试
```

性能自测（在页面控制台里跑）：

```js
// 河的 RAF 先注册，所以这里的 now - ts 就包含它这一帧的开销
const d = [];
await new Promise(done => { let i = 0;
  requestAnimationFrame(function t(ts) { d.push(performance.now() - ts);
    if (++i >= 60) return done(); requestAnimationFrame(t); }); });
d.sort((a, b) => a - b);
console.log('中位', d[30].toFixed(2), 'ms');   // 应在 4~6ms
// 对照：滚到底让河离开视口再跑一次，应降到 0.5ms 左右
```
