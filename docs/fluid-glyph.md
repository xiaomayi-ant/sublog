# 流体字形 —— 404 页的水，以及它和河的分工

> 代码：`src/lib/fluidGlyph.mjs`（WebGL 着色器 + 2D 遮罩合成）
> 使用处：`src/pages/404.astro`
> 测试：`tests/not-found-contract.test.mjs`、视觉基线 `notfound-1440x900`

---

## 1. 它是什么

404 页那个巨大的「404」不再是一块实色，而是**盛着水的字形**。水在字里流动，字形边缘保持锐利。

页面文案本来就是「这条水路没有抵达这里。」—— 水的隐喻早就写在那儿，只是过去是静止的。现在水路没有抵达，但水还在动。

---

## 2. 为什么不是把首页那条河搬过来

两套东西，模型不同，各自解决不同的问题。

| | `riverRenderer`（首页） | `fluidGlyph`（404） |
|---|---|---|
| 渲染 | Canvas 2D | WebGL 片元着色器 |
| 驱动 | **几何** —— 中心线 + 缎带 | **场** —— 每像素求值 |
| 流动来自 | 虚线相位沿固定路径平移 | 域扭曲场本身随时间演化 |
| 运动维度 | 一维位移 | 二维拉伸、卷曲、折叠 |
| 成本 | CPU 4.0ms/帧 | GPU 0.8ms/帧 |

**河的流动感不足，根因在模型而不在参数。** 它的 50 条纤维是静止路径，动的只是描在上面的虚线相位——这是一维位移，缺少真流体必备的平流、涡量和折叠。这不是调参能补的，是渲染模型的边界。

`fluidGlyph` 用的是另一条路：两层噪声 `w1`/`w2` 各自带时间项，再拿它们去偏移采样坐标 `q`。扭曲场自己在演化，纹理被拉伸、卷起、再合上。

**但没有因此去重写河。** 河那套模型换来了别的东西：可解析的河岸、曲率软钳制、各向异性校正，以及 15 条压在纯函数上的数学测试。用场模型重写，那些全部作废。两者留着各做各的。

## 3. 配色：直接吃河的色阶

字形的三档颜色不是另抄的，是从 `riverRenderer` 导入的 `WASH_LADDER` 前三档：

```js
palette: {
  shallow: WASH_LADDER[0].rgb,   // [222, 252, 250]
  mid:     WASH_LADDER[1].rgb,   // [140, 240, 236]
  deep:    WASH_LADDER[2].rgb,   // [78, 212, 228]
}
```

**两处同源，不是两处同步。** 河改色，这边跟着走。这一点有契约测试守着：色阶的字面值只能存在于河渲染器那个 chunk 里，404 的脚本必须 import 它而不是复制一份 —— 抄一份进去测试立刻变红（验证过）。

河与 `tokens.css` 就因为靠注释同步而漂过（见 `river-math.md` 第 5.4 节），这次不重蹈。

### 为什么用声明色而不是河的观感色

河在屏幕上实际是什么颜色，量过（首页河面 18170 个像素采样）：

| | 最浅 p05 | 中位 | 最深 p95 |
|---|---|---|---|
| 河面实际 | `#feffff` | `#c9eef6` | `#bfe8f4` |

范围窄到只有一档半 —— 因为它是八层各自 alpha 0.03~0.09 叠出来的。**照搬这个范围放进字形，纹理几乎读不出来，等于白做流体。**

所以取的是渲染器声明的那三档原色。落地后的实测：

| | 字形 | 河面实际 |
|---|---|---|
| 中位 | `#d0f9f8` | `#c9eef6` |
| p75 | `#c2f7f5` | `#c2eaf5` |
| p95 | **`#7ae1ea`** | `#bfe8f4` |

整体重量与河基本一致（中位、p75 都对得上），差别在深端多出一大截 —— 那正是纹理能读出来的原因。残留差异是色相倾向：字形偏青绿（G>B），河偏青蓝。

## 4. 白底上的关键：合成模型必须是减色的

参考项目 `fluidglass-ui` 的材质在白底上会塌成脏灰。实测过：把它的 demo 底色换成白、文字换成赭墨，卡片立刻变成灰色团块。

根因在它着色器的最后几行 —— `cyanGlow *= .78 + .25*haze` 配 `alpha ≤ 0.92` 的低透明度亮青，这是**"暗底上发光"的加色逻辑**。低 alpha 的亮色合成到白底上，数学结果就是灰。

所以能拿走的是**技术**（fbm + 域扭曲），不是**材质**。这里的合成换成水彩：

```
pigment = mix(shallow, mid, …)   // 越深表示颜料越多
pigment = mix(pigment, deep, …)  // 而不是越亮
```

颜料吸收光，密度高的地方颜色更重。这与站点既有的美学是同一套（首页的河也是这么做的）。

## 5. 高光

白纸上打白色高光等于没打。所以高光必须是**"深色区域里的一道亮"**。

位置取密度的**过渡带**：

```glsl
float rim = smoothstep(0.30, 0.52, density) * (1.0 - smoothstep(0.52, 0.80, density));
```

过渡带正是场变化最快的地方，等价于沿梯度找边界。

**为什么不用 `dFdx`/`dFdy`**：第一版就是那么写的，结果整段着色器编译失败——WebGL1 里屏幕空间导数需要 `OES_standard_derivatives` 扩展，而本机的 ANGLE Metal 后端不支持它。过渡带的做法不需要任何扩展，而且零额外成本。

`tests/not-found-contract.test.mjs` 里有一条测试专门守着别再退回去。

## 6. 遮罩：为什么是两块画布

字形遮罩用 **2D 画布的 `destination-in`**，不是 SVG mask：

1. WebGL 在离屏画布上渲染流体
2. 可见的 2D 画布 `drawImage` 把它拷过来
3. `globalCompositeOperation = 'destination-in'` 再 `fillText('404')`，流体被裁进字形

排版参数（字体、字号、字距）从 DOM 的 `getComputedStyle` 读，因为字号是 `clamp(6rem, 25vw, 15rem)` 算出来的，不能在这边另写一套。

SVG mask 的问题是它依赖 SVG 内的字体解析结果与 CSS 一致，跨浏览器不保证。多一次 `drawImage` 的代价可以忽略——画布只有字那么大（约 752×360）。

## 7. 降级：这一页最重要的性质

404 是**用户走错路时看到的那一页**。装饰失败时页面仍然完好，比装饰好看重要得多。

DOM 里的静态数字既是底稿也是降级形态：

```html
<div class="number-stack" data-fluid-glyph aria-hidden="true">
  <p class="number">404</p>        <!-- 默认可见，浅水色实色 -->
  <canvas class="number-fluid"></canvas>
</div>
```

只有 `createFluidGlyph` 真的接管了，脚本才把 `data-fluid-glyph` 置为 `on`，CSS 才隐藏静态数字。任何一条失败路径都自动回到改动前的样子，一行 JS 都不必执行。

**两条降级路径都实测过，不是推断的**：

| 路径 | 复现方式 | 结果 |
|---|---|---|
| 拿不到 WebGL 上下文 | headless Chrome 加 `--disable-gpu` | `data-fluid-glyph` 保持为空，静态数字照常 |
| 着色器编译失败 | 开发中真撞到过（`dFdx` 那次） | 同上，页面完好 |

视觉基线 `notfound-1440x900` 锁的正是**降级形态**（截图带 `--disable-gpu`）。这是有意的取舍：GPU 渲染结果跨机器不稳会假红，而"没有 WebGL 时 404 仍然完好"才是最该钉死的性质。

## 10. 融合实验：河道不动，内里换成流体

问题：能否在**保持首页河流形态不变**的前提下，把流体场融进去？

**架构上是通的，而且改动极小。** 关键观察是河的 `compositeRibbon` 本来就在做遮罩 —— `traceRibbon` 把河道填成白色蒙版，再用 `source-in` 灌颜色。这与字形的 `destination-in` 是同一套机制，只是遮罩的形状不同。

实验页：`/lab/river`（noindex），上下两条河用**同一套几何** —— 同一条中心线、同一组河宽、同一批缎带半径与图层不透明度。开关是 `createRiverRenderer({ fluidInterior: true })`，默认关闭。

### 走过的两条路

**先试了"取代"**：八层缎带全部灌流体，不再灌纯色。

结果：形态完全对得上，但整条河淡掉一大截且发绿。两个原因 ——
1. 让密度直接当不透明度（`floor 0 / span 1`），八层叠完只有原来的四成；
2. 更要命的是八层共用同一张流体，而流体的平均色是浅的，**原本由深层贡献的 `#4ed4e4` / `#4298e4` 全丢了**。

**改成"叠加"**：每层先按原样灌自己的颜色，再用 `source-atop` 把流体叠上去，强度由 `FLUID_TEXTURE_STRENGTH` 控制（现取 0.5）。

颜色结构是这条河的骨架，不能让纹理顶掉。`source-atop` 保证一笔不落在缎带之外。

### 量化结果

| | 现状 | 融合 |
|---|---|---|
| 覆盖像素 | 9176 | **9176（100% 一致）** |
| 中位色 | `#cdeef6` | `#d9f3f9` |
| p95 | `#bde5f5` | `#c0ecf5` |

**覆盖像素逐个相同** —— 这是形态被完整保留最硬的证据：河道、河岸、弯度一个像素没动，变的只是内里填什么。

两条满幅河同时渲染：**60.9 fps**（画布 2354×539，dpr 2）。

### 安全性

默认关闭。关闭时**四张视觉基线逐像素不变**（首页两张、lab 一张、404 一张），也就是说这次实验没有碰到首页一个像素。

### 未定的事

- 融合版整体仍略浅于现状（中位 `#d9f3f9` vs `#cdeef6`）
- 纤维与焦散层原样保留，没有考虑它们与流体纹理是否重复
